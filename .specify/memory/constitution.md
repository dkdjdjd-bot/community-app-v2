## Core Principles

### I. 테스트 우선 (Test First)
<!-- NON-NEGOTIABLE -->
모든 기능은 테스트를 먼저 작성한 후 구현합니다.
- TDD 필수: 테스트 작성 → 사용자 승인 → 테스트 실패 확인 → 구현
- Red-Green-Refactor 사이클을 엄격히 준수
- 테스트 없는 기능은 완료로 인정하지 않음
- 단위 테스트, 통합 테스트, E2E 테스트를 단계별로 작성

### II. 사용자 중심 (User-Centric)
사용자 경험을 최우선으로 설계합니다.
- 모든 기능은 사용자 시나리오에서 출발
- 사용자 피드백을 빠르게 반영할 수 있는 구조 유지
- 직관적이고 일관된 인터페이스 제공
- 접근성(A11y)을 기본으로 고려

### III. 단순함 (Simplicity)
불필요한 복잡성을 피하고 명확한 코드를 작성합니다.
- YAGNI 원칙: 필요하지 않은 기능은 구현하지 않음
- 코드는 읽기 쉽고 의도가 명확해야 함
- 과도한 추상화보다 명시적인 코드를 선호
- 단순한 해결책부터 시작하고 필요할 때 확장

### IV. 보안 (Security)
인증/인가 및 데이터 보호를 기본으로 합니다.
- 모든 API 엔드포인트에 적절한 인증/인가 적용
- 사용자 입력은 항상 검증하고 살균(sanitize)
- 민감한 데이터는 암호화하여 저장
- 보안 이벤트는 반드시 로깅

## 품질 기준

커뮤니티 앱의 품질을 보장하기 위한 기준을 정의합니다.

- 모든 코드는 리뷰를 거쳐야 머지 가능
- 테스트 커버리지는 핵심 비즈니스 로직에서 80% 이상 유지
- 성능: 페이지 로드 2초 이내, API 응답 500ms 이내
- 에러 상황에 대한 사용자 친화적 메시지 제공

## 개발 워크플로우

일관된 개발 프로세스를 통해 품질과 협업을 보장합니다.

- Feature 브랜치 기반 개발: `###-feature-name` 형식
- spec-kit을 활용한 명세 우선 개발 (Specification → Plan → Tasks → Implementation)
- 커밋 메시지는 변경 의도를 명확히 전달
- PR은 관련 spec 및 테스트 결과를 포함

## Governance

이 Constitution은 Community App V2 프로젝트의 모든 개발 관행에 우선합니다.
- 모든 PR/리뷰에서 Constitution 준수 여부를 확인
- 복잡성 증가는 반드시 정당화되어야 함
- 수정 시 문서화, 승인, 마이그레이션 계획 필요
